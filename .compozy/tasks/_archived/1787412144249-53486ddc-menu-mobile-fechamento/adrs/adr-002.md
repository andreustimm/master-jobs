# ADR-002: Client component dedicado ao menu mobile, fechamento por event delegation

## Status

Accepted

## Date

2026-08-21

## Context

O PRD (ADR-001) decidiu fechar o menu mobile ao navegar, com o mínimo de
JavaScript de cliente. A exploração do codebase revela um precedente forte:
`app/theme-switch.tsx` e `app/locale-switch.tsx` já são client components que
fecham seus popovers com `hidePopover()` — o padrão "script mínimo para fechar
popover" já existe no projeto. A invariante "zero JavaScript" já tem exceções
pontuais para popover; o menu mobile será mais uma, do mesmo tipo.

O desafio técnico específico: `MobileNav` e `NavLinks` vivem hoje no mesmo
arquivo (`app/nav-links.tsx`), sem `"use client"`. `NavLinks` também é usado na
fileira desktop (um componente server), então pôr `"use client"` no topo do
arquivo empurraria a fileira desktop inteira para o bundle de cliente — um custo
que o defeito não pede.

## Decision

1. **Mover `MobileNav` para um arquivo próprio** `app/mobile-nav.tsx`, marcado
   com `"use client"`, que importa `NavLinks` de `app/nav-links.tsx`.
   `nav-links.tsx` continua server (sem `"use client"`), preservando a fileira
   desktop como está.

2. **Fechamento por event delegation**: um único `onClick` no `<nav>` que
   embrulha os links chama `hidePopover()` (via
   `document.getElementById(id)?.hidePopover?.()`), o mesmo idioma de
   `theme-switch` e `locale-switch`. Um handler cobre todos os itens — presentes
   e futuros — sem tocar em cada `Link`, e sem interceptar a navegação (o
   `Link` do Next.js segue fazendo SPA normalmente).

3. **Testes**: o caso e2e (Playwright, `tests/e2e/ui.mjs`) ganha uma verificação
   que abre o menu em 375px, clica num item e afirma que `#menu-mobile` não está
   mais visível. Os testes de nó em `tests/nav-mobile.test.ts` que hoje afirmam
   "sem `"use client"`" e "`MobileNav` em `nav-links.tsx`" precisam ser
   atualizados para o novo endereço do componente.

## Alternatives Considered

### Alternative 1: `"use client"` no topo de `nav-links.tsx`

- **Description**: Marcar o arquivo inteiro como client component.
- **Pros**: Menos arquivos; o componente não se move.
- **Cons**: `NavLinks` é compartilhado com a fileira desktop, que passaria a
  entrar no bundle de cliente sem necessidade — custo de hidratação que o
  defeito não pede.
- **Why rejected**: Custo desproporcional; a separação mantém o limite de
  cliente exatamente onde ele é necessário.

### Alternative 2: Prop de fechamento atravessando `NavLinks`

- **Description**: `NavLinks` ganha uma prop `onNavigate` repassada a cada
  `Link` como `onClick`.
- **Pros**: Fechamento explícito por item.
- **Cons**: Toca o componente compartilhado (a fileira desktop precisaria
  passar uma prop nula), e um `Link` novo que esquecer o repasse reintroduz o
  defeito silenciosamente.
- **Why rejected**: Event delegation é um ponto único, cobre itens futuros de
  graça e não altera `NavLinks`.

### Alternative 3: Fechar após a navegação (efeito em `usePathname`)

- **Description**: Observar a mudança de rota e fechar o popover num `useEffect`.
- **Pros**: Sem handler de clique.
- **Cons**: Fecha *depois* da navegação — a tela já trocou; há uma janela em que
  o menu cobre o conteúdo novo. Mais frágil (depende do ciclo do React e do
  router), e introduz um efeito para algo que um `onClick` resolve no gesto.
- **Why rejected**: O PRD exige fechamento no mesmo gesto, antes da pintura da
  tela nova.

## Consequences

### Positive

- A fileira desktop permanece server; só o menu mobile vira client.
- Um handler único; `NavLinks` fica intocado e continua a fonte única dos links
  para os dois menus.
- Reusa o idioma `hidePopover()` já estabelecido, sem inventar padrão novo.

### Negative

- Mais um arquivo na árvore `app/`, e o componente `MobileNav` muda de endereço —
  os testes de nó que o referenciam precisam ser atualizados.

### Risks

- O `onClick` no `<nav>` pode fechar o popover num clique que não navega (ex.:
  clique em área morta do menu). Mitigação: o menu inteiro é composto de links;
  a área morta é mínima, e fechar nela é inofensivo (o usuário já decidiu
  interagir com o menu).
- O fechamento depende de `hidePopover` existir no navegador. O projeto já usa o
  encadeamento opcional `?.hidePopover?.()` em dois lugares; seguir o mesmo
  idioma garante degradação segura (sem fechamento, sem erro) em navegadores
  antigos.

## Implementation Notes

- A forma exata do handler (`onClick` inline vs. função nomeada) e o teste de nó
  a atualizar ficam para o TechSpec e o contrato de testes.
- O id `menu-mobile` continua o mesmo, para o e2e e o CSS não mudarem de alvo.
