# ADR-004: Generate a Credentialless Standalone Offline Document

## Status

Accepted

## Date

2026-08-23

## Context

The existing service worker precaches `/offline` and `/login` with `cache.addAll()`. Those requests use same-origin credentials. Both routes inherit the dynamic root layout, which reads the current session and can render role-specific navigation, account state, and impersonation state. A response intended as a public offline shell must not be capable of carrying session-derived markup into persistent Cache Storage.

The offline contract also needs a retry path and localized copy while remaining available when the Next.js server and application bundles cannot be reached. Caching an ordinary React route would preserve unnecessary dependencies and make privacy depend on the correctness of a dynamic layout.

## Decision

Generate a standalone `/offline.html` document during the existing service-worker generation step. The committed source is a pure renderer under `src/core/pwa/offline.ts`; `scripts/sw-version.mjs` writes the derived document beside `public/sw.js`. The renderer reuses the splash brand primitives, embeds only the two typed locale copies and non-sensitive semantic styling, and contains no session, route, user, or API data.

The service worker precaches `/offline.html` with an explicit `Request` using `credentials: "omit"`. `/login` is removed from the shell cache. Static caching is narrowed to the explicit precache allowlist and `/_next/static/`; file extensions alone never qualify a same-origin URL for persistent storage.

A failed full-document navigation returns the cached standalone document while the browser retains the originally requested URL, so its retry control can call `location.reload()` and perform a fresh authorized request. A failed App Router payload remains network-only and causes the service worker to notify the requesting client with a typed `navigation-offline` message. The active transition then shows its localized offline phase and retries with a hard navigation to the active target. No failed route payload is synthesized or cached as a successful RSC response.

## Alternatives Considered

### Alternative 1: Continue Caching the React `/offline` Route

- **Description**: Keep the existing offline page and make its UI match the splash.
- **Pros**: Reuses ordinary React rendering and application CSS.
- **Cons**: The route inherits session-aware root markup and depends on application assets that may be unavailable offline.
- **Why rejected**: A credentialless, session-independent cache entry is a security property, not a styling preference.

### Alternative 2: Cache `/login` as the Offline Shell

- **Description**: Display the login page when navigation fails.
- **Pros**: No additional document.
- **Cons**: Suggests authentication can proceed offline, may cache redirected/session-aware markup, and does not explain connectivity failure.
- **Why rejected**: It is neither an honest offline outcome nor a safe static shell.

### Alternative 3: Enable Next.js `experimental.useOffline`

- **Description**: Let Next.js detect failures and automatically retry router requests and Server Actions.
- **Pros**: Framework-managed retry and connectivity handling.
- **Cons**: Changes mutation retry semantics globally and does not enforce the selected explicit offline screen and fresh-retry policy.
- **Why rejected**: Automatic Server Action retry expands behavioral and data-integrity risk beyond the PRD.

### Alternative 4: Return Plain Text from the Service Worker

- **Description**: Keep only the current `503` text fallback.
- **Pros**: Small and robust.
- **Cons**: Not localized, branded, retryable, or equivalent to the requested transition experience.
- **Why rejected**: It remains only the last-resort fallback when the standalone document is unavailable.

## Consequences

### Positive

- Persistent offline HTML is provably independent of authentication and user data.
- Full offline starts work without React hydration, Next route data, external fonts, or a live server.
- Soft-navigation failure remains explicit and retry retrieves fresh authorized content.
- Cache eligibility changes from a broad filename heuristic to a reviewable allowlist.

### Negative

- The standalone document duplicates a deliberately small subset of shell markup and CSS because it cannot depend on the dynamic application layout.
- Build generation gains a second derived artifact that must remain synchronized with its committed renderer.
- Soft and hard navigation failures use different presentation containers, although both share the same copy and brand contract.

### Risks

- A future renderer change could accidentally include user data. Tests inspect generated response bodies using seeded sensitive markers, not only cache keys.
- Storage refusal can prevent offline installation. Installation remains non-blocking and the service worker falls back to a non-sensitive plain `503` response.
- A service-worker message may arrive after a newer navigation. The client accepts it only when its normalized target matches the current generation.

## Implementation Notes

- The generated document chooses `pt-BR` or English from the non-sensitive locale cookie, then browser language, and defaults to `pt-BR`.
- Escape all translated text before embedding it in HTML or script data.
- Preserve the existing versioned cache retirement on `activate`.
- Keep `/api/`, `/admin/`, `/candidate`, `/pipeline`, `/referrals`, `/compare`, `/p/`, exports, App Router payloads, and every non-allowlisted navigation out of Cache Storage.
