# ADR-005: Reconcile Accepted Server Action Redirects at Route Commit

## Status

Accepted

## Date

2026-08-24

## Context

ADR-003 selected `onRouterTransitionStart` plus typed navigation adapters and
assumed the hook covered Server Action redirects. Browser proof against the
installed Next 16.3.2 production build showed a narrower runtime contract: the
hook runs for `push`, `replace`, and `traverse`, but the Server Action reducer
applies an accepted redirect through its internal navigation path without
calling the public hook.

Starting on form submission would be wrong because the mutation may not
redirect. Wrapping, replaying, intercepting `fetch`, or patching History would
also violate the one-shot mutation and stable-boundary decisions. Leaving the
gap open would make successful login, recovery, comparison, job creation, and
impersonation redirects change screens without the required transition.

## Decision

Keep the two intent-level start paths from ADR-003: the documented router hook
and the typed GET adapters. Add one compatibility reconciliation at the route
observer, which already owns committed pathname/search reporting:

1. In a layout effect, compare the prior route key with the committed key.
2. If the route changed and the store is idle, begin the missing accepted
   redirect using the prior URL only as the classification base.
3. If a previous generation has already committed, allow the newly committed
   history destination to take ownership.
4. If a newer target remains uncommitted, do nothing; its authoritative start
   must not be replaced by a stale commit.
5. In the existing normal effect, report URL commit so the root loading
   signal's layout effect retains readiness precedence.

`begin(url, currentOverride?)` exposes the classification base needed by this
single coordinator call. Adapters and instrumentation continue to call the
one-argument form. Same-target coalescing preserves a single generation when
the public hook did run.

POST Server Action forms remain ordinary forms. Reconciliation observes only
a route Next has already accepted and committed; it never starts on submit,
intercepts the response, replays the mutation, or automatically retries it.

## Consequences

### Positive

- Real Next 16.3.2 behavior satisfies the accepted-redirect contract without
  weakening one-shot mutation semantics.
- The compatibility path stays inside the existing coordinator and uses the
  same generation/reducer rules as hook and adapter starts.
- Rapid committed history traversal can transfer ownership while stale commits
  cannot replace an uncommitted target.

### Negative

- A Server Action redirect begins immediately before paint of the committed
  route rather than at router intent time because Next exposes no earlier
  public signal on this path.
- The observer now reconciles framework behavior in addition to reporting
  readiness, so its guard requires explicit integration and browser coverage.

### Risks and Mitigations

- **Future Next versions begin emitting the hook for Server Actions:**
  same-target coalescing makes reconciliation idempotent; the installed-version
  contract tests must still be revalidated on upgrade.
- **A stale commit arrives after a newer navigation begins:** the observer
  refuses to begin while the active generation is uncommitted.
- **A POST is replayed:** no submission or response interception exists, and
  browser tests assert one POST per redirecting action.

## Verification

- IT-012 locks ordinary Server Action forms, observer ownership guards, and
  same-target coalescing.
- E2E-004 submits five real redirecting actions and asserts one POST and one
  transition for each accepted redirect.
- E2E-005 and E2E-008 prove rapid ownership and stale-generation rejection.

## Supersedes

Only ADR-003's factual assertion that the Next 16.3.2 public hook observes
Server Action redirects. The hybrid hook/adapters architecture, commit plus
fallback readiness, and all privacy/accessibility decisions remain unchanged.
