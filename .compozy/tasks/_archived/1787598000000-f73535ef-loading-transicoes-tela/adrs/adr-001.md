# ADR-001: Use One Full-Screen Splash Contract for First-Party Navigation

## Status

Accepted

## Date

2026-08-23

## Context

Master Jobs already presents a branded, localized splash during a full document load, but client-side route changes provide no equivalent feedback. Users can click the desktop or mobile menu and see the previous screen remain in place while the destination is being prepared. Applying the startup splash's current 900 ms minimum literally to every route would make already-ready destinations feel slower, while showing a loader only on the global menu would leave contextual links, redirects, filters, and browser history inconsistent.

The product must provide one predictable transition experience across every first-party route and every supported device without inventing a second loading visual.

## Decision

Every user-initiated first-party screen transition uses the existing Master Jobs splash identity as a full-screen, interaction-blocking loading state. This includes desktop and mobile menus, internal links and cards, redirects after forms, URL-backed view changes, and browser back/forward navigation. It applies to authenticated areas, authentication and recovery routes, and public profiles. External destinations, theme changes, modals, and disclosure controls are not screen transitions and do not invoke it.

Transition timing is adaptive rather than a literal copy of startup timing. The splash appears when a navigation is accepted, remains for a short anti-flicker interval, and leaves when the destination is ready. It does not impose the startup splash's 900 ms minimum. After three seconds, the localized status changes from the normal loading message to an honest prolonged-wait message. The loading state never disappears merely because a fixed timer elapsed while the destination is still pending.

If navigation fails, the splash leaves, the application restores or keeps a usable screen, and the user receives a localized error. Native browser controls remain available. The latest accepted navigation owns the loading state; a stale completion cannot dismiss a newer transition.

## Alternatives Considered

### Alternative 1: Copy the Startup Timing Literally

- **Description**: Reuse both the splash visual and its 900 ms minimum/3 s maximum on every navigation.
- **Pros**: Exact behavioral match; simple mental model.
- **Cons**: Delays instant and prefetched routes; may expose the previous screen while work continues after the timer.
- **Why rejected**: The user chose the same visual identity with adaptive duration rather than an artificial delay.

### Alternative 2: Show Loading Only for the Global Menu

- **Description**: Attach the splash only to desktop and mobile navigation links.
- **Pros**: Narrow scope and immediate improvement for the reported interaction.
- **Cons**: Contextual links, cards, form redirects, filters, and history remain inconsistent.
- **Why rejected**: The user explicitly chose all internal screen transitions.

### Alternative 3: Keep the Header Interactive

- **Description**: Replace only the page body with a loading state while preserving the menu.
- **Pros**: Users can interrupt one navigation with another app action.
- **Cons**: Does not match the requested splash experience and allows duplicate or conflicting actions against the previous screen.
- **Why rejected**: The user chose a full-screen, blocking transition.

## Consequences

### Positive

- Navigation has one recognizable visual contract on desktop, mobile, PWA, authenticated, and public surfaces.
- Fast routes are not artificially slowed by the startup splash's timing.
- Slow, failed, interrupted, and superseded transitions have explicit user-visible outcomes.
- Existing theme, locale, safe-area, and reduced-motion behavior remains authoritative.

### Negative

- The app interface is temporarily unavailable during an accepted transition.
- The transition lifecycle must coordinate several navigation entry points rather than only global menu links.
- Automated tests can no longer bypass every splash indiscriminately; startup and transition states need separate observability.

### Risks

- A missed completion signal could cover the interface indefinitely; failure and recovery behavior must be independently verifiable.
- Prefetched routes may complete before a framework pending signal becomes visible; the transition contract must not depend on one entry point alone.
- Concurrent or superseded navigation may dismiss the wrong overlay; ownership must follow the latest accepted destination.

## Implementation Notes

The TechSpec must choose the integration compatible with the repository's installed Next.js version after consulting its local documentation. It must preserve the visual source of truth in `src/core/pwa/splash.ts`, typed translations, server-component boundaries where possible, and real-browser verification at desktop and 375 px mobile widths.
