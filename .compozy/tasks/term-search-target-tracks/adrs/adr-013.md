# ADR-013: Pay Normalization for the Jobs Screen Is Computed in SQL From the Money Module's Constants

## Status

Accepted

## Date

2026-09-18

## Context

PRD rules 36–40 add a minimum-pay filter and a normalized sort by pay. Jobs
store `comp_min`, `comp_max`, `comp_currency` and `comp_period`; there is no
project duration column, so project pay is never annualizable from stored data.
`src/core/money.ts` defines `PERIODS_PER_YEAR` (hour 2080, day 260, week 52,
month 12) and `convert` over an `FxTable`; `loadRates(base)` in the FX context
returns the latest rates for a base. Sort by pay today orders by the raw
`coalesce(comp_max, comp_min)` (`repo.ts:185-190`). Filtering and sorting must
run in the database to keep paging and counts correct.

## Decision

- `src/core/money.ts` exports `annualFactorSql()`: a SQL `CASE` built from
  `PERIODS_PER_YEAR`, so SQL and TypeScript share one table of factors.
- The board query receives the target currency, the target period and the
  latest FX table (`loadRates("USD")`) as a `VALUES (currency, rate)` list. It
  computes, per job, `pay_top_annual_usd = coalesce(comp_max, comp_min) *
  factor / rate(currency)` and converts to the target currency and period.
  Missing currency rate, unknown period or `project` period yields NULL
  ("not comparable"); missing amount yields NULL ("not disclosed").
- The filter keeps a job when its normalized top reaches the minimum, or when it
  is NULL and the "only with disclosed pay" toggle is off; NULL rows sort after
  the qualifying rows, then by fit, then by `job.id`.
- The conversion never feeds the scorer or a compensation range.

## Alternatives Considered

### Alternative 1: Materialize a normalized column on `job`

- **Description**: Store `pay_top_annual_usd` at ingestion and on FX refresh.
- **Pros**: Indexable.
- **Cons**: Must be recomputed on every FX refresh; another write path to keep
  consistent.
- **Why rejected**: The corpus size does not need an index for this filter.

### Alternative 2: Filter in TypeScript after the query

- **Description**: Load rows, convert with `money.convert`, filter in memory.
- **Pros**: Reuses `convert` directly.
- **Cons**: Breaks database paging and counts.
- **Why rejected**: Correct totals require filtering in the query.

## Consequences

### Positive

- One factor table; sort and filter agree with the displayed converted amount.

### Negative

- Project pay stays "not comparable" until a source provides a duration.

### Risks

- A stale FX table shifts converted values; the Jobs screen shows the rate date
  next to converted amounts.

## Implementation Notes

The display value next to each job uses `money.convert` on the same FX table, so
the shown amount equals the filtered amount.
