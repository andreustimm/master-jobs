# ADR-009: A Track Is a Target Fragment Merged With the Person Profile; Accepted Tracks Score Only Relevant Jobs

## Status

Accepted

## Date

2026-09-18

## Context

`scoreJob(input, ctx)` in `src/core/scoring/score.ts` is pure and reads one
`Profile` (`src/core/profile/schema.ts`). Its inputs split cleanly: target-level
fields (`targets.clusters`, `targets.avoid_titles`, `keywords`,
`seniority.min_years_expected`, `seniority.reject_below_years`,
`compensation.ranges`, `compensation.reference_currency`) and person-level
fields (`constraints`, `blockers`, `compensation.project`,
`compensation.benefits`, `seniority.years_experience`, `evidence`, `growth`,
`cv`). `candidate_matching_profile` stores one `profile_json` per candidate, has
no editor, and a derived profile inherits the default profile's targets,
compensation and evidence without a marker. With six tracks, scoring every job
for every track multiplies `job_score` rows by six on a storage-limited
database; the user chose to score accepted tracks only where they are relevant.

## Decision

- A new table `target_track` stores, per track, a `TrackTarget` JSON with the
  target-level fields only. `candidate_matching_profile` keeps the person-level
  fields. `effectiveProfile(person, target)` merges them into a `Profile` and
  parses it with `ProfileSchema`; the scorer does not change shape.
- The primary track scores every open job, as today. An accepted track scores a
  job only when at least one of its target titles or positive keywords appears
  in the job's title or description with the whole-word pattern of ADR-012
  (`isRelevant(target, text)`). A job with no row on a track is outside that
  track; the job detail computes the missing track's fit on demand and does not
  persist it.
- The candidate's own matching profile becomes the primary track exactly once.
  A candidate without an own profile gets a pending primary track (no target)
  and is never scored. Target fields that a derived profile inherited from the
  default profile are listed in `target_track.unreviewed_json` until saved.
- Track suggestions are a pure function of the term, the skills catalog and the
  candidate's own evidence.

## Alternatives Considered

### Alternative 1: Score every job on every track

- **Description**: One row per job per active track.
- **Pros**: Literal reading of the original rule.
- **Cons**: Up to six times the rows and recalculation time.
- **Why rejected**: The user chose the relevance gate; irrelevant jobs would sit
  under any cut anyway.

### Alternative 2: Tracks as an array inside `profile_json`

- **Description**: Keep one row per candidate with a `tracks` array.
- **Pros**: No new table.
- **Cons**: Every track edit rewrites the whole row; no foreign key from
  `job_score` or `saved_term` to a track.
- **Why rejected**: Tracks need an identity other rows reference.

## Consequences

### Positive

- The scorer, its tests and its reasons stay as they are; only inputs change.
- The M-06 loophole closes: scoring requires a primary track with a target, and
  `scoreAll` no longer falls back to the default profile.

### Negative

- Two places hold profile data (person and track); the merge is the only
  supported read path.
- Changing an accepted track's titles or keywords changes which jobs it scores.

### Risks

- Relevance uses title and description only; a job whose company name holds
  the only hit is not scored on that track. The scorer never used the company
  name, so fits stay consistent.

## Implementation Notes

`profile_hash` becomes the hash of the effective profile per track, so the
existing staleness rule (version, hash, age) works per track unchanged.
`ensureMatchingProfile` writes the person fields and upserts the primary track.
