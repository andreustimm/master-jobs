# ADR-007: Term Captures Run Through a Table-Backed Queue Drained by `after()` and by the Daily Sweep

## Status

Accepted

## Date

2026-09-18

## Context

PRD rule 14 requires the first run of a saved term to start within one minute.
The runtime has no continuous worker: Vercel functions stop at 30 seconds
(`vercel.json`), the only Vercel cron is daily (`/api/cron/recheck`, 10:00
UTC), and the GitHub sweep (`.github/workflows/varredura.yml`) runs once a day
and is paused in production. Every existing "run now" action only enqueues
(`recheckAction` in `app/actions.ts:87-101`). The roadmap invariant forbids a
second pipeline: "A rota de cron não pode virar um segundo pipeline… lógica vai
para src/core/, e os dois chamadores compartilham." Next.js 16 `after()` runs a
callback after the response, within the route's `maxDuration`.

## Decision

Term captures are rows in a durable queue table, `term_capture`, one row per
(platform, normalized term, UTC day). Saving or re-running a term enqueues the
rows for every reachable platform and schedules `after(() =>
runTermCaptures({ budgetMs: 25_000, worker: "web" }))` in the same Server
Action invocation. The daily sweep gains one step, `jho terms run`, that
enqueues the day's captures for every active term and drains the queue with the
same `runTermCaptures` function. Claims use `FOR UPDATE SKIP LOCKED` with a
lease; an expired lease is reclaimable by any later drain. The queue sits behind
a `TermCaptureQueuePort` in `src/contexts/sourcing/ports.ts`, because ADR 0009
names a hosted queue as the expected replacement when the web runtime needs it.

## Alternatives Considered

### Alternative 1: Vercel cron every minute

- **Description**: A cron route drains the queue every minute.
- **Pros**: Independent of user requests.
- **Cons**: Requires the Vercel Pro plan; 1,440 invocations a day with no work
  most of the time; a second scheduled entry point.
- **Why rejected**: Plan dependency and idle cost for a capability `after()`
  already provides.

### Alternative 2: Dispatch the GitHub workflow from the app

- **Description**: The action calls `workflow_dispatch` through the GitHub API.
- **Pros**: Runs outside the 30-second limit.
- **Cons**: Stores a repository write token in the app; 30–90 seconds of cold
  start; competes with the sweep's concurrency group; the workflow takes no
  inputs today.
- **Why rejected**: Security surface and latency for a job that fits in one
  platform call.

### Alternative 3: Wait for the next daily sweep

- **Description**: No immediate run.
- **Pros**: No new trigger.
- **Cons**: Breaks PRD rule 14 and US-007 AC-2.
- **Why rejected**: The first run is when the candidate is paying attention.

## Consequences

### Positive

- One capture function serves web and sweep; no second pipeline.
- A crashed `after()` loses nothing: the row stays claimable.

### Negative

- A drain inside `after()` shares the invocation's 30-second ceiling; long
  platform responses may spill into the next drain.

### Risks

- If neither a later `after()` nor the sweep runs (sweep paused in production),
  spilled rows wait. Mitigation: every save or re-run drains pending rows first;
  the Searches screen shows "daily repeat paused" when no sweep has enqueued
  captures for 36 hours.

## Implementation Notes

`runTermCaptures` stops claiming when less than 5 seconds of `budgetMs` remain.
The lease is 5 minutes. The sweep step runs after `jobs sync` and before scoring,
so captured jobs are scored in the same sweep.
