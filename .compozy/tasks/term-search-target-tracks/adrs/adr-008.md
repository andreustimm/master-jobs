# ADR-008: Per-Track Fit Lives in `job_score`, Keyed by Track

## Status

Accepted

## Date

2026-09-18

## Context

Target tracks (ADR-002) give each candidate one fit per track and job. Today
`job_score` has primary key `(candidate_id, job_id)` (`schema.ts:201`), carries
`scorer_version` and `profile_hash`, and is read by the board, cockpit,
pipeline (including the recruiter view), dossier, statistics, CSV export,
markdown report, gap analysis, skills target corpus, referrals and the
cross-candidate `max(fit)` queries in verify and scrape. PRD rule 30 requires
single-fit readers to use the primary track. ADR 0007 defines the fit
assessment identity as `(CandidateId, JobPostingId, CalibrationVersion)`.

## Decision

Add `track_id` to `job_score` and make the primary key
`(candidate_id, track_id, job_id)`, with an index on
`(candidate_id, track_id, fit)`. Every reader resolves a track through one
matching-context helper, `trackScope(candidateId, choice)`, that returns the
primary track by default, a chosen track, or "all tracks" (best row per job),
and exposes `scoreTrackFilter(scope)`, the SQL predicate readers append.
Cross-candidate `max(fit)` queries read primary-track rows only. The migration
is expand → backfill → contract: add a nullable column, create each candidate's
primary track and backfill its id, set NOT NULL, then swap the primary key. ADR
0007's fit identity becomes `(CandidateId, TrackId, JobPostingId,
CalibrationVersion)`.

## Alternatives Considered

### Alternative 1: Side table for accepted tracks

- **Description**: `job_score` keeps the primary track; `job_track_score` holds
  accepted tracks.
- **Pros**: Additive migration; existing readers untouched.
- **Cons**: One concept in two tables; "all tracks" becomes a UNION; changing
  the primary track moves or recomputes rows between tables.
- **Why rejected**: Promoting a track is a routine user action and must not move
  data.

### Alternative 2: Compute accepted-track fits at read time

- **Description**: Persist nothing for accepted tracks.
- **Pros**: No migration.
- **Cons**: Scoring 10,000 jobs per request breaks the 2-second target and
  prevents sorting and paging in the database.
- **Why rejected**: Performance.

## Consequences

### Positive

- One model; promoting a track changes a flag, not rows.
- Rule 30 is enforced in one helper instead of in each reader.

### Negative

- Every `job_score` reader and the E2E fixtures change.
- The first PostgreSQL migration with a backfill and a primary-key swap;
  automatic promotion to staging suspends for human review.

### Risks

- A reader missed by the refactor would mix tracks. Mitigation: readers keep
  their SQL, but an architecture test requires every source file that
  references `jobScore` (outside `schema.ts`, the scoring writer and the
  migration) to also reference `scoreTrackFilter`, the SQL predicate the helper
  exports.

## Implementation Notes

Follow `.claude/skills/drizzle-safe-migrations`: a custom migration for the
backfill, generated migrations for the column and the key. The legacy SQLite
precedent 0011 → 0012 → 0013 shows the same sequence for `candidate_id`.
