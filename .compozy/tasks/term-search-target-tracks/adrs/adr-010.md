# ADR-010: A Durable Per-Platform Quota Ledger With Atomic Reservation, Shared by Sync and Term Captures

## Status

Accepted

## Date

2026-09-18

## Context

PRD rule 18 sets per-platform budgets for the whole system, counting every call
to the platform, regular sync included (Remotive: 4 a day, 2 a minute). Three
runtimes can call platforms: the web `after()` drain, the CLI, and the sweep.
No quota table exists. The only in-repo limiter (`src/core/rate-limit.ts`) is
in-memory per process; the login limiter counts `auth_event` rows then inserts,
which is not atomic. `realGetJson` (`src/core/sources/http.ts:46-87`) retries
429 and 5xx up to twice, so one logical call can become three real calls that
the caller never sees.

## Decision

- A table `platform_quota(platform, window_kind, window_start, used)` with
  primary key `(platform, window_kind, window_start)`; `window_kind` is `day`
  (UTC date) or `minute` (UTC minute).
- `reserve(platform, budget, now)` runs, for each window kind the budget
  declares, one statement:
  `INSERT … VALUES (…, 1) ON CONFLICT DO UPDATE SET used = used + 1 WHERE
  platform_quota.used < :limit RETURNING used`. No row returned means the window
  is full. The day reservation happens first; a full minute window after a
  successful day reservation releases the day unit.
- A reservation precedes every network call to a budgeted platform, in term
  captures and in `syncOne` for adapters that declare a budget. Budgeted calls
  use `retries: 0`; a failed call keeps its unit spent and is retried in a later
  window by the queue.
- A 429 response records `paused_until` for the platform (the day-window row
  moves to `used = limit`), so no further call happens that UTC day.
- Budgets are declared by the adapter (`termSearch.budget`) as data; the ledger
  sits behind `PlatformQuotaPort`.

## Alternatives Considered

### Alternative 1: In-memory limiter

- **Description**: Reuse `createRateLimiter`.
- **Pros**: No table.
- **Cons**: Per process; the web runtime, the CLI and the sweep each get a full
  budget.
- **Why rejected**: The budget is per system.

### Alternative 2: Count-then-insert over a log table

- **Description**: Log each call and count before calling, as the login limiter
  does.
- **Pros**: Doubles as history.
- **Cons**: Not atomic; two drains can both pass the count.
- **Why rejected**: Concurrency correctness is the point of the ledger.

## Consequences

### Positive

- The budget holds across runtimes, restarts and concurrent drains.
- Hidden retries no longer spend quota the ledger did not see.

### Negative

- The regular Remotive sync now competes with term captures for 4 daily calls:
  the two configured keyword sources leave 2 for terms (PRD rule 18).

### Risks

- A reservation followed by a crash wastes a unit; acceptable against the
  alternative of exceeding the platform's terms.

## Implementation Notes

The ledger prunes rows older than 7 days during `reserve`. Reservation happens
synchronously before the network `await`, following the "reserve the slot
before the await" rule in AGENTS.md.
