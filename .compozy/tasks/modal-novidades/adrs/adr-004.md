# ADR-004: Isolate browser-only behavior in a client modal

## Status

Accepted

## Date

2026-08-22

## Context

The existing footer is a Server Component that reads `USER_CHANGELOG.md` and
renders a native popover without shipping application JavaScript. The new
requirements need browser state and browser APIs: independently expanded cards,
a deterministic reset on every opening, a true modal focus boundary, and date
conversion using the device timezone. A Server Component cannot observe the
device timezone or own interactive React state.

Moving the complete footer or changelog loading path to the client would solve
the interaction but would also move filesystem-independent work and a global
layout surface across the client boundary unnecessarily.

## Decision

Keep changelog file selection, disk reading, parsing, and label resolution in
the server-rendered footer. Add a narrowly scoped Client Component that receives
only serializable release records, the active locale, resolved labels, and the
current application version.

The client component will use the native `<dialog>` element through
`showModal()` and `close()`. It will own the open cycle, focus restoration,
backdrop dismissal, and a `Set<string>` of expanded version identifiers. Every
open operation initializes that set with only the newest release. Browser-local
date formatting occurs inside this boundary after hydration.

## Alternatives Considered

### Alternative 1: Preserve popover and add imperative DOM scripts

- **Description**: Keep the server-only markup and attach independent scripts for local time and expansion reset.
- **Pros**: Retains most existing markup and avoids a React client component.
- **Cons**: Scatters lifecycle state across DOM events, provides weaker modal semantics, and makes focus/reset behavior harder to test coherently.
- **Why rejected**: The requirements form one interactive lifecycle and should have one state owner.

### Alternative 2: Move the entire footer to the client

- **Description**: Fetch or embed all footer and changelog behavior in one Client Component.
- **Pros**: One rendering model and straightforward access to browser APIs.
- **Cons**: Expands hydration to unrelated global UI and cannot read the canonical Markdown files directly.
- **Why rejected**: Next.js recommends keeping client boundaries narrow, and server-side file loading remains the correct integration boundary.

### Alternative 3: Keep zero JavaScript

- **Description**: Use static `<details>` and server-formatted dates only.
- **Pros**: Preserves the current zero-JavaScript property.
- **Cons**: Cannot know the device timezone and cannot guarantee reset-on-open plus the required modal lifecycle.
- **Why rejected**: It cannot satisfy the accepted product behavior.

## Consequences

### Positive

- Browser-only behavior has one explicit owner and a small hydration footprint.
- Native dialog semantics provide top-layer rendering, focus containment, and Escape handling.
- Server code remains responsible for canonical content and locale selection.
- Pure state and formatting helpers remain independently testable.

### Negative

- The footer now ships a client bundle for the What's New interaction.
- The trigger becomes interactive only after hydration.
- Backdrop dismissal and explicit focus restoration still require component logic around the native dialog.

### Risks

- Formatting device-local time during SSR would create hydration mismatches. Instant formatting must occur only after the client timezone is available.
- Passing the translator function across the boundary would violate React serialization. Resolve labels before constructing client props.
- A dialog can be visually modal but still mishandle focus. End-to-end coverage must assert entry, containment, Escape, and restoration.

## Implementation Notes

- `app/footer.tsx` remains a Server Component and passes serializable props to `app/changelog-modal.tsx`.
- The client props must not include functions, filesystem handles, or raw parser errors.
- The dialog header remains visible while the release list scrolls.
- The trigger retains the existing footer location and localized label.
