# ADR-005: Store locale editions separately and render with react-markdown

## Status

Accepted

## Date

2026-08-22

## Context

The application has typed `pt-BR` and `en` interface dictionaries, but release
prose is editorial history rather than component copy. Putting years of notes
inside the typed dictionaries would make both code review and authoring worse.
The existing custom CV Markdown preview is a limited regular-expression parser:
it does not model nested blocks and does not reject unsafe link protocols.

The changelog needs full CommonMark-style editorial blocks, safe links, no raw
HTML execution, and a release gate that prevents one locale from publishing
without the other.

## Decision

Rename the current Portuguese source to `USER_CHANGELOG.pt-BR.md` and add
`USER_CHANGELOG.en.md`. Both remain canonical hand-authored Markdown documents.
They must contain the same visible version identifiers and publication metadata;
the release preparation path validates this parity before writing any release
outputs. The active server locale selects exactly one file at render time.

Add `react-markdown` as the production renderer. Do not enable raw-HTML plugins.
Provide explicit component mappings for product typography and spacing, plus a
URL transform that allows only approved relative URLs and `http`, `https`, and
`mailto` schemes. The renderer receives a complete release body rather than
physical source lines.

## Alternatives Considered

### Alternative 1: One combined bilingual Markdown file

- **Description**: Nest Portuguese and English blocks inside each release.
- **Pros**: One file guarantees version adjacency.
- **Cons**: Harder to review as a coherent document, requires custom locale syntax, and sends unrelated language content through parsing.
- **Why rejected**: Locale-per-file matches the existing application convention and keeps editorial review readable.

### Alternative 2: Generate English automatically during release

- **Description**: Keep Portuguese canonical and translate English at publication time.
- **Pros**: Maintainers author only one edition.
- **Cons**: Introduces an LLM or translation-service dependency into the release gate and cannot guarantee reviewed equivalent language.
- **Why rejected**: Publication must remain deterministic and auditable without an external provider.

### Alternative 3: Extend the custom CV Markdown parser

- **Description**: Generalize the existing regular-expression renderer.
- **Pros**: No new production dependency and total control of output.
- **Cons**: Reimplements mature block parsing and security edge cases; the current parser already demonstrates structural limitations.
- **Why rejected**: A proven renderer is smaller in maintenance risk than a growing bespoke Markdown dialect.

## Consequences

### Positive

- Each locale is a readable, reviewable source document.
- Multiline Markdown and nested editorial structure render correctly.
- Raw HTML stays inert by default and unsafe protocols are blocked explicitly.
- Structural release parity becomes enforceable before publication.

### Negative

- Every user-facing change requires two maintained files.
- `react-markdown` adds a production dependency and client-bundle weight inside the modal boundary.
- Semantic translation equivalence still requires human review; automation can prove structure and metadata, not meaning.

### Risks

- One file missing from the standalone build would silently remove a locale. Both paths must be declared in output tracing and covered by integration tests.
- Localized files can drift in content while passing version-set validation. Review guidance and matched release structure mitigate, but cannot fully automate, semantic parity.

## Implementation Notes

- Interface labels stay in `src/core/i18n/pt-BR.ts` and `src/core/i18n/en.ts`; release prose does not move into them.
- `next.config.ts` must trace both localized Markdown files.
- Existing historical Portuguese notes require reviewed English translations.
- Tables, task lists, footnotes, and embedded rich media remain outside the guaranteed subset.
