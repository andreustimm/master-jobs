# ADR-017: Limits counted in the new tables under a per-candidate advisory lock; directory search limited per recruiter

## Status

Accepted

## Date

2026-10-06

## Context

Decided by the agent under the goal of 2026-10-06, implementing ADR-006 and
the directory rate limit left to the TechSpec by ADR-010.

Serverless instances share nothing in memory. `password-login.ts` limits by
"record, then count" so that N concurrent attempts see each other, and
`drizzle-tracks.ts` serializes with `pg_advisory_xact_lock`. G13 asks that a
limit under concurrency reserve the slot before the `await` that performs the
effect.

## Decision

- **Candidate cap (10 per rolling 24 h)** and **pending invitations (20)**:
  every grant, invite and resend runs in a transaction that first takes
  `pg_advisory_xact_lock(hashtext('recruiter-access'), candidate_id)`, then
  counts `recruiter_access_event` rows with `actor = 'candidate'` and `kind IN
  ('grant_created', 'invite_sent', 'invite_resent')` in the last 24 h, and
  pending unexpired invitations. Over the cap → `cap_reached` with `retryAt`
  = oldest counted entry + 24 h; nothing is written. Refused attempts,
  revocations, cancellations, acceptances and administrator actions write no
  counted entry.
- **Recruiter suggestion cap (20 per candidate per rolling 24 h)**: same lock
  on the candidate, counting the recruiter's `recruiter_suggestion_by` rows
  for that candidate in the last 24 h.
- **Directory search (60 per recruiter per 10 min)**: record, then count, in
  `recruiter_directory_query` (ADR-011). The 61st request in the window
  renders "Try again shortly" with no results; pagination counts as a search.
- Values are constants in the pure domain modules, not environment variables.

## Alternatives Considered

### Alternative 1: In-memory limiter (`src/core/rate-limit.ts`)

- **Cons**: Per instance; useless on Vercel.
- **Why rejected**: Must hold across instances.

### Alternative 2: Separate counter table for the candidate cap

- **Cons**: Duplicates what the history already records.
- **Why rejected**: The history is the ledger.

## Consequences

### Positive

- Concurrent requests at the limit never exceed it (US-025.EC-2).

### Negative

- Grants of one candidate serialize; negligible at expected volume.

### Risks

- The history-based count depends on every counted action writing its entry
  in the same transaction; asserted by integration tests.

## Implementation Notes

The lock key pair `(hashtext('recruiter-access'), candidate_id)` is shared by
grant, invite, resend and suggestion creation for that candidate.
