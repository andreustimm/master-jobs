# ADR-009: Recruiters become users invited by candidates, working from the existing candidate list

## Status

Accepted

## Date

2026-10-06

## Context

`docs/product/personas.md` describes P2 (Camila, the recruiter) as "not a
user"; `docs/product/vision.md` says the product "is not multi-tenant today".
With #464 recruiters can sign up and with this feature they receive access from
candidates. Bullhorn-style agency tools make the agency the owner of candidate
data; here the candidate owns the data and decides who sees it.

Decided by the owner on 2026-10-06.

## Decision

- The recruiter is a user invited by the candidate. The candidate remains the
  owner of their data; access is always granted, scoped and revocable by them.
- A recruiter with several candidates picks one from the existing list at
  `/recruiter`; the candidate's name appears in the title of that candidate's
  page.
- Vision and personas docs are updated when the feature ships to state this,
  without describing the product as a multi-tenant agency tool.

## Alternatives Considered

### Alternative 1: Candidate switcher in the header

- **Pros**: Faster switching for recruiters with many candidates.
- **Cons**: New navigation component for a small population.
- **Why rejected**: The list already serves; owner decision.

### Alternative 2: Agency-owned workspace

- **Description**: Recruiter organizations own candidate records.
- **Why rejected**: Contradicts candidate ownership, the product's
  differentiator.

## Consequences

### Positive

- Clear ownership story for users and for LGPD.

### Negative

- The candidate's name becomes visible to recruiters in page titles, which is
  intended within a grant.

### Risks

- Docs drifting from behavior; the docs update ships with the feature (rule
  23).

## Implementation Notes

The name shown is the candidate's display name, marked as user content.
