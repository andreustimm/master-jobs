# ADR-015: Suggestions become funnel entries only through the candidate's accept, in one transaction

## Status

Accepted

## Date

2026-10-06

## Context

Decided by the agent under the goal of 2026-10-06, implementing ADR-003.

Rule 2 keeps ingestion away from `application`. The precedent for a proposal
the person accepts is `mail_suggestion` + `decideSuggestion`
(`src/core/mail/run.ts`): one transaction, `FOR UPDATE` on the row, a
conditional status UPDATE, and `setApplicationStatusInTransaction`
(`src/core/db/repo.ts`) for the funnel write. `application` has a unique
`(candidate_id, job_id)` and a free `channel` column (`direct | ats |
referral | recruiter | agency`). `createRecruiterJobAction`
(`app/jobs/new/actions.ts`) registers a job and redirects to `/jobs/<id>`.

## Decision

- A suggestion is a `recruiter_suggestion` row (one per pending
  candidate+job) plus one `recruiter_suggestion_by` row per suggesting
  recruiter (ADR-011). A second recruiter suggesting the same pending job adds
  a `_by` row to the same suggestion.
- Accept runs in one transaction: lock the suggestion `FOR UPDATE` scoped to
  the session's candidate; if not `pending`, return `already_decided`; if no
  `application` exists for the job, insert it through
  `setApplicationStatusInTransaction(tx, candidateId, jobId, 'backlog',
  'sugestão de recrutador #<id>', stamp, 'recruiter')`; if one exists, leave
  its status and channel untouched; set `status = 'accepted'`,
  `application_id`, `decided_at`; append `suggestion_accepted` history.
- The "suggested by a recruiter" marker lives on the suggestion: the funnel
  entry shows it by joining `recruiter_suggestion.application_id`. `channel =
  'recruiter'` is written only when the accept created the application.
- Decline sets `declined` and appends history; the funnel is never read or
  written.
- Creating a suggestion never touches `application`. The recruiter can
  suggest from the candidate page (catalog search) or from `/jobs/new` with a
  `suggestFor` field. Both actions take a candidate id only as a selector and
  accept it only when it is in `session.linkedCandidateIds` (the policy
  decides with `suggestion:create` on `{ kind: 'candidate', candidateId }`);
  any other id answers the same 404 as an unknown candidate (G40: the scope is
  the session's; the id only picks inside it).
- With `suggestFor`, `createRecruiterJobAction` creates the job, then the
  suggestion, and redirects to `/recruiter/<id>`; without it, behavior is
  unchanged.

## Alternatives Considered

### Alternative 1: Reuse `mail_suggestion`

- **Pros**: Existing UI and decision code.
- **Cons**: It is tied to a mail message and a suggested status transition;
  recruiter identity, note and multi-recruiter join do not fit.
- **Why rejected**: Different source and shape.

### Alternative 2: Create the application at suggestion time in a hidden state

- **Pros**: Simpler accept.
- **Cons**: Violates rule 2 and pollutes funnel counts the recruiter sees.
- **Why rejected**: Rule 2.

### Alternative 3: Always set `channel = 'recruiter'` on accept

- **Cons**: Overwrites the candidate's own channel on an existing entry.
- **Why rejected**: Accept must not change an existing entry (US-021.EC-2).

## Consequences

### Positive

- Rule 2 holds; accept is idempotent under double submit (one row lock).

### Negative

- The marker needs a join on the funnel query.

### Risks

- A reviewer reading G40 literally may flag the selector id; the TechSpec
  registers both actions in the entry inventory with the session check as
  the control, and `tests/entry-denial.test.ts` gains the non-linked id case.

## Implementation Notes

The recruiter sees only `_by` rows whose `grant_id` is their current active
grant for that candidate, so suggestions of an ended grant disappear for them
and stay with the candidate (US-017.AC-3, EC-3).
