# ADR-011: Data model — additive grant, invitation, history and suggestion tables; `recruiter_candidate` frozen

## Status

Accepted

## Date

2026-10-06

## Context

Decided by the agent under the goal of 2026-10-06.

`recruiter_candidate` (`src/core/db/schema.ts`) holds one row per
(recruiter, candidate) with a unique index on the pair, `ON DELETE CASCADE` on
the recruiter, and `unlinkById` deletes the row. The PRD needs states (active,
revoked, expired, ended by account removal), an optional end date with its
time zone, the last access, invitations for people without an account, an
append-only history that survives recruiter removal (G20), and job suggestions
with several suggesting recruiters. Re-granting creates a new grant (ADR-007),
which the unique pair index forbids. Changing that table in place (dropping
the index, swapping CASCADE for SET NULL, adding status) is a non-additive
migration that stops the promotion for human review (G51).

## Decision

Add five tables and one rate-limit log, all additive, in one migration:

- `recruiter_grant` — id; `candidate_id` → candidate **CASCADE**;
  `recruiter_user_id` → auth_user **SET NULL**; `recruiter_email` (normalized);
  `status` `active | revoked | expired | ended_account_removed` (CHECK);
  `invite_id` → recruiter_invite **SET NULL**; `created_by` → auth_user
  **SET NULL**; `created_at`; `expires_at` (ISO UTC, null = no end);
  `expiry_tz`; `ended_at`; `revoked_by` → auth_user **SET NULL**;
  `last_accessed_at`. Unique partial `(candidate_id, recruiter_user_id) WHERE
  status = 'active'`; CHECK `status <> 'active' OR recruiter_user_id IS NOT
  NULL`; index `(recruiter_user_id, status)`.
- `recruiter_invite` — id; `candidate_id` → candidate **CASCADE**; `email`
  (normalized); `token_hash` (SHA-256, unique); `status` `pending | accepted |
  expired | cancelled | superseded` (CHECK); `expires_at` (7 days);
  `access_expires_at`, `expiry_tz` (the end date chosen at invite time);
  `created_by`, `cancelled_by`, `accepted_user_id` → auth_user **SET NULL**;
  `created_at`, `decided_at`, `delivery_failed_at`, `dismissed_at`. Unique
  partial `(candidate_id, email) WHERE status = 'pending'`.
- `recruiter_access_event` — append-only history: id; `candidate_id` →
  candidate **CASCADE**; `grant_id`, `invite_id`, `suggestion_id` → **SET
  NULL**; `recruiter_email` (denormalized, NOT NULL); `kind` (CHECK, list in
  the TechSpec); `actor` `candidate | admin | recruiter | system` (CHECK);
  `actor_user_id` → auth_user **SET NULL**; `actor_name` (administrator name
  snapshot); `detail`; `at`. Index `(candidate_id, at desc, id desc)`.
- `recruiter_suggestion` — id; `candidate_id` NOT NULL → candidate
  **CASCADE**; `job_id` NOT NULL → job **CASCADE**; `status` `pending |
  accepted | declined` (CHECK); `application_id` → application **SET NULL**;
  `created_at`, `decided_at`. Unique partial `(candidate_id, job_id) WHERE
  status = 'pending'`.
- `recruiter_suggestion_by` — id; `suggestion_id` → recruiter_suggestion
  **CASCADE**; `recruiter_user_id` → auth_user **SET NULL**; `recruiter_email`;
  `grant_id` → recruiter_grant **SET NULL**; `note` (CHECK `char_length(note)
  <= 500`); `created_at`; `notified_at`. Unique `(suggestion_id,
  recruiter_user_id)`; index `(recruiter_user_id, created_at)`.
- `recruiter_directory_query` — id; `recruiter_user_id` → auth_user
  **CASCADE**; `at`. Only a timestamp per directory search, for the rate limit
  (ADR-017); no query text, no candidate.

Existing links move by an additive `INSERT … SELECT` in the same migration:
each `recruiter_candidate` row becomes an `active` grant (email from
`auth_user`, `created_by` and `created_at` kept, no end date) with one
`grant_created` history entry (`actor = 'system'`). From then on
`recruiter_candidate` receives no writes and no reads.

**Pending:** dropping `recruiter_candidate` is a non-additive migration and
belongs to a later issue with human review. It is not removed here.

## Alternatives Considered

### Alternative 1: Alter `recruiter_candidate` in place

- **Description**: Add status, dates and email; drop the unique pair index;
  switch the recruiter FK to SET NULL.
- **Pros**: One table, no copy.
- **Cons**: Dropping an index and changing a FK action are non-additive; the
  promotion waits for review; old and new code disagree during deploy.
- **Why rejected**: The additive path ships through the automatic promotion.

### Alternative 2: Store invitations as grants with a null recruiter

- **Description**: One table with `status = 'invited'`.
- **Pros**: Fewer tables.
- **Cons**: Token, link validity, delivery state and resend chain do not
  belong to a grant; every access query must exclude invitations.
- **Why rejected**: Mixing them makes the access query easy to get wrong.

### Alternative 3: History in `auth_event`

- **Pros**: Table exists.
- **Cons**: `auth_event` is an operator audit keyed by user, pruned by
  retention, and has no candidate scope; the candidate must page their own
  history.
- **Why rejected**: Different owner, scope and lifetime.

## Consequences

### Positive

- Every PRD state is a column value; re-granting is a new row.
- History survives recruiter removal (email denormalized, FKs SET NULL) and
  disappears with the candidate (CASCADE), as the PRD asks.

### Negative

- `recruiter_candidate` lingers until the follow-up removal.

### Risks

- An administrator unlinking through the old code between migration and
  deploy would delete the old row but leave the grant active. Mitigated by the
  short window and by the admin revoke on the new code.

## Implementation Notes

The migration is generated by `drizzle-kit` plus a hand-written data step in
the same file; the upgrade test (pattern of
`tests/migration-target-tracks.test.ts`) seeds a
`recruiter_candidate` row before migrating and asserts the grant and the
history entry. Every FK declares `ON DELETE` in the schema and the DDL (G20).
