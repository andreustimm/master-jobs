# ADR-013: Profile directory behind `candidate:discover`, built on a shared allowlist builder

## Status

Accepted

## Date

2026-10-06

## Context

Decided by the agent under the goal of 2026-10-06, implementing ADR-010.

`publicProfile(slug)` (`src/core/candidate-public.ts`) reads one candidate by
`public_slug`, refuses anything but `visibility = 'public'`, and builds the
allowlist: name, headline, location and links through `containsContact()`,
confirmed skills, opt-in facts (`publicFactsFrom`), photo and cover versions,
and the CV through `publicCvMarkdown()` (which applies `publicCvText()`
twice) when `public_cv` is on. `can()` has a `candidate:read` branch for
`visibility = 'recruiters'` that no route uses. `candidate` has no trigram
index; skills live in `candidate_skill` + `skill`. The job search composes
`parseQuery` (`src/core/search.ts`), `termRegexSql` (`src/core/term.ts`) and
`~*` with a trigram prefilter (`src/core/db/repo.ts`).

## Decision

- New policy action **`candidate:discover`**: allowed only for sessions with
  the recruiter role (borrowed sessions included: an administrator
  impersonating a recruiter sees what that recruiter sees). Candidate-only,
  administrator-only and anonymous sessions are denied.
- Refactor `publicProfile()` into `allowlistedProfile(key, visibilities)`,
  where `key` is `{ slug }` or `{ id }` and `visibilities` is a non-empty
  subset of `['recruiters', 'public']` fixed by the caller in code.
  `publicProfile(slug)` becomes `allowlistedProfile({ slug }, ['public'])`.
  The row-to-profile mapping moves to a pure function shared by the profile
  page and the directory card, so the directory cannot select a field the
  public profile does not release.
- Routes: `/recruiter/directory` (search, filters, pagination),
  `/recruiter/directory/[id]` (profile, by candidate id), and
  `/recruiter/directory/[id]/image/[kind]` (photo and cover, same allowlist).
  Each calls `requirePage("candidate:discover")` first. The visibilities are
  constants in the server module; no request parameter reaches them.
- Search (`src/core/candidate-directory.ts`): free text up to 200 characters,
  parsed by `parseQuery`; each valid term must match, case- and
  accent-insensitively, the name, the headline or a confirmed skill name
  (regex from `termRegexSql` over accent-folded text). Filters: location text,
  and work model and experience level only where the matching `public_*`
  opt-in is on. Ordered by name then id; 20 per page. No trigram index: the
  set is bounded by the visibility filter.
- Results never count or hint at Private profiles. Any invalid filter value is
  dropped. If text was given but no valid term remains, the result is empty.
- A Public profile shows its `/p/` link; a Recruiters profile does not. A
  recruiter who also holds a grant sees a link to the grant page.
- Reading the directory writes nothing about the candidate.

## Alternatives Considered

### Alternative 1: Reuse `candidate:read` with visibility

- **Pros**: No new action.
- **Cons**: `candidate:read` with `visibility = 'public'` allows any session,
  so a candidate-only session would pass; listing is not reading one profile.
- **Why rejected**: The directory must be recruiter-only (US-029.AC-2).

### Alternative 2: Separate directory projection

- **Description**: A second field list for the directory.
- **Pros**: Smaller cards.
- **Cons**: Two allowlists drift (US-031.EC-2).
- **Why rejected**: One builder, one list.

### Alternative 3: Full-text index (`tsvector`)

- **Pros**: Ranking.
- **Cons**: New index and language config; the job search already settled on
  regex + trigram.
- **Why rejected**: Bounded set, consistent semantics with job search.

## Consequences

### Positive

- G21–G23 hold by construction for the directory.
- The unused `recruiters` branch of `candidate:read` gains a real consumer.

### Negative

- Candidate ids appear in directory URLs; unknown and Private ids answer the
  same 404.

### Risks

- Bulk harvesting; mitigated by the rate limit (ADR-017) and pagination.

## Implementation Notes

The directory page enters `tests/e2e/routes.mjs`; the id pages enter
`UNMEASURED_PAGES` with the reason (fixture-dependent ids, exercised by the
directory spec). `PAGE_POLICY` lists the three entries with their guards.
