# ADR-012: Access is cut only where the session loads it; ending a grant is an UPDATE

## Status

Accepted

## Date

2026-10-06

## Context

Decided by the agent under the goal of 2026-10-06.

`linkedCandidatesFor` (`src/contexts/auth/infra/drizzle-store.ts`) is the only
reader of recruiter links. Every session resolution (`drizzleSessions.resolve`,
password login, magic link) calls it, and the result becomes
`session.linkedCandidateIds`. `can()`, `/recruiter` and `/recruiter/[id]`
receive these ids already filtered and never query links themselves. The
administrator screens read links through `linkedCandidates`/`linksOf`
(`drizzle-directory.ts`) and remove one through `unlinkById`, a physical
DELETE. The PRD requires the cut on the recruiter's next request (no
background delay), forward-only endings, and a history that survives.

## Decision

- `linkedCandidatesFor(userId, roles)` reads `recruiter_grant` with
  `recruiter_user_id = userId AND status = 'active' AND (expires_at IS NULL OR
  expires_at > now)`, `now` from `clock()`. Without the recruiter role it keeps
  returning `[]`; a disabled account keeps failing in `resolve()` before it.
  This one predicate is the cut for revocation, expiry, role removal and
  account disabling. No cache sits in between.
- The administrator reads (`linkedCandidates`, `linksOf`) use the same
  predicate. `unlinkById` is replaced by `revokeGrant(grantId, by)`.
- Every ending is a conditional UPDATE on `status = 'active'` with
  `RETURNING`, inside a transaction that appends the history entry. The
  second of two concurrent endings updates zero rows and reports
  `already_ended`; only the winner writes history and sends the email.
- Expiry is enforced by the predicate the instant `expires_at` passes; the
  hourly sweep (ADR-016) only flips the status to `expired`, writes the
  history and sends the email.
- Removing a recruiter account ends its active grants as
  `ended_account_removed` in the same transaction as the delete
  (`UserDirectory.remove`), before the FK sets the user to null.
- `last_accessed_at` is updated when the recruiter opens the candidate page or
  the CV, at most once per minute per grant.

## Alternatives Considered

### Alternative 1: Check the grant at every use site

- **Description**: Pages and actions query `recruiter_grant` themselves.
- **Pros**: The freshest possible answer per call.
- **Cons**: Several queries that must agree; one forgotten site leaks.
- **Why rejected**: The session is already the single point the policy trusts.

### Alternative 2: Keep the DELETE

- **Pros**: Simple.
- **Cons**: Loses the grant's history and the reason it ended.
- **Why rejected**: LGPD art. 18 VII and US-012.

## Consequences

### Positive

- One predicate decides access, and it is tested directly.
- A request authorized before the revocation may finish; the next one is
  denied (US-008.EC-2).

### Negative

- Each session resolution keeps one extra indexed query (as today).

### Risks

- A future reader that skips the predicate. Mitigated by an architecture test
  that only `drizzle-store.ts`, `drizzle-directory.ts` and the access store
  import `recruiterGrant`.

## Implementation Notes

`linkRecruiterToCandidate` (used only by `tests/e2e/setup.mjs`) writes an
active grant with a `system` history entry; it stays out of every web and CLI
surface.
