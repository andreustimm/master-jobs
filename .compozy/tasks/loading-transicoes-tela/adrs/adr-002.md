# ADR-002: Keep Offline Support Shell-Only and Free of Private Content

## Status

Accepted

## Date

2026-08-23

## Context

Navigation feedback must remain coherent when connectivity disappears. Master Jobs handles resumes, applications, salary expectations, administrative data, and revocable public profiles. Persisting visited authenticated screens in a service-worker cache would leave copies on disk after logout, session expiry, public-profile revocation, or device loss. Clearing cache during a normal logout cannot cover those cases.

The user requested offline cache support and selected a safe shell rather than automatic storage of previously viewed private screens.

## Decision

Offline support caches only non-sensitive application-shell resources required to render the established Master Jobs identity and a dedicated offline outcome. This includes eligible static assets such as the app icon and locally controlled shell resources. It never caches authenticated HTML, route payloads, APIs, exports, public profiles, or user data.

When a first-party navigation cannot complete because the device is offline, the transition splash leads to a localized offline screen instead of remaining indefinitely or exposing a stale private page as if it were current. A full offline start follows the same safe path. Reconnection and retry must produce an ordinary fresh navigation rather than replaying sensitive cached content.

## Alternatives Considered

### Alternative 1: Cache the Last Visited Screens

- **Description**: Store authenticated screens and show them when offline.
- **Pros**: More data appears available without a network connection.
- **Cons**: Private and revocable content persists on disk outside current authorization; stale content can look current.
- **Why rejected**: It violates the product's security-by-absence policy and the user's selected safe-shell scope.

### Alternative 2: User-Selected Offline Packs

- **Description**: Let users explicitly download selected jobs or profile content.
- **Pros**: Consent is explicit and the offline value is higher than a shell alone.
- **Cons**: Requires a separate lifecycle for download, expiry, revocation, deletion, and device storage.
- **Why rejected**: The user chose shell-only cache for this feature. Explicit offline packs remain a possible future feature, not an implicit extension.

### Alternative 3: No Offline Cache

- **Description**: Allow navigation to fail with the browser's default network error.
- **Pros**: No service-worker storage or offline lifecycle.
- **Cons**: Breaks the branded transition, produces an inconsistent PWA experience, and gives no actionable recovery path.
- **Why rejected**: The user explicitly requested offline cache support.

## Consequences

### Positive

- The app has a coherent and branded offline failure path without weakening privacy.
- Logout, session expiry, profile revocation, and lost-device scenarios do not depend on cache cleanup to protect user data.
- Reconnection always retrieves authorized, current content.

### Negative

- Users cannot read previously visited jobs, profiles, or pipeline data offline.
- Offline support is a recovery experience rather than full offline productivity.

### Risks

- A broad cache rule could accidentally admit route payloads; tests must verify cache names and runtime behavior, not only configuration text.
- Third-party resources may be unavailable offline; the shell must remain understandable without depending on an uncached external asset.
- An offline fallback that resembles a valid destination could mislead users; it must state clearly that current content is unavailable.

## Implementation Notes

The existing service-worker privacy invariant remains unchanged. The TechSpec must preserve network-only handling for authenticated routes, APIs, exports, and `/p/`, and must verify offline behavior in an installed/mobile-sized context as well as desktop.
