# ADR-003: Coordinate Navigation Transitions with a Next Router Hook and Typed Adapters

## Status

Accepted

## Date

2026-08-23

## Context

The feature must start one transition lifecycle for prefetched links, URL-backed controls, programmatic navigation, browser traversal, and redirects emitted by Server Actions. A root `loading.tsx` boundary cannot supply that contract by itself: prefetched destinations can skip the fallback, and the fallback observes rendering rather than the accepted navigation. `useLinkStatus` is link-local and does not cover history or redirects.

Next.js 16.3 exposes `onRouterTransitionStart` from `instrumentation-client.ts`. It observes App Router `push`, `replace`, and `traverse` transitions before React commits the destination. The hook is documented, but router-transition instrumentation was introduced as an experimental capability. Depending on it without a project-owned boundary would make a framework upgrade capable of silently removing navigation coverage.

The repository otherwise favors typed, explicit UI boundaries and keeps pages as Server Components. The solution must preserve that property and cannot convert the root application into a client-rendered tree.

## Decision

Use a small client-side transition coordinator with two complementary start paths:

1. Root `instrumentation-client.ts` forwards `onRouterTransitionStart(url, navigationType)` into the coordinator. This is the authoritative path for programmatic navigation, browser traversal, prefetched links, and Server Action redirects.
2. Project-owned `TransitionLink` and `TransitionGetForm` adapters wrap first-party links and GET navigation forms. They use stable Next.js public components and provide an idempotent fallback start signal for the routes they own.

The coordinator coalesces duplicate starts for the same active target, assigns a monotonically increasing generation to a genuinely newer destination, and ignores completions from older generations. A root observer built from `usePathname()` and `useSearchParams()` records URL commit. A client signal rendered by root `loading.tsx` records whether the route fallback is mounted. The transition becomes ready only after the destination commits and no root fallback remains, then observes the 180 ms anti-flicker minimum already used by the repository's route view transition.

The implementation does not enable `experimental.instrumentationClientRouterTransitionEvents`; the additional metadata is unnecessary. A compatibility test locks the two-argument hook contract against the installed Next.js version. The root application remains a Server Component; only the coordinator/presenter is a client island.

## Alternatives Considered

### Alternative 1: Typed Adapters Only

- **Description**: Migrate every link, form, router call, and history path to project-owned wrappers without using the router hook.
- **Pros**: Uses only stable public component APIs; every adapted call site is visible in code review.
- **Cons**: Cannot precisely observe redirects produced after Server Actions, requires bespoke history handling, and makes future omissions likely.
- **Why rejected**: It cannot provide the PRD's exhaustive redirect and traversal coverage without either showing loading during unrelated mutations or intercepting the DOM globally.

### Alternative 2: Router Hook Only

- **Description**: Start every transition exclusively through `onRouterTransitionStart`.
- **Pros**: Smallest integration surface and complete App Router coverage.
- **Cons**: Leaves the application with no stable project-owned navigation boundary if the experimental hook changes.
- **Why rejected**: The user selected a hybrid design with typed adapters and an explicit fallback surface.

### Alternative 3: Root `loading.tsx` and `useLinkStatus`

- **Description**: Let framework fallbacks and link-local pending state drive the splash.
- **Pros**: No instrumentation hook and little custom state.
- **Cons**: Prefetched links may not report pending, history and redirects are incomplete, and ownership across superseded transitions is undefined.
- **Why rejected**: It cannot satisfy the full PRD scope.

### Alternative 4: Global DOM Interception

- **Description**: Capture every document click, submit, and history event and infer whether it represents an internal transition.
- **Pros**: Few call-site edits.
- **Cons**: Reimplements browser and Next routing rules, risks classifying modifiers/downloads/external links incorrectly, and is difficult to type or test exhaustively.
- **Why rejected**: The project should integrate at router and component boundaries rather than infer intent from arbitrary DOM events.

## Consequences

### Positive

- One generation-based state machine covers links, redirects, and history while preserving Server Components.
- Typed adapters make first-party navigation intent searchable and give ordinary link/form paths a stable fallback.
- Framework compatibility becomes an explicit test rather than an undocumented assumption.
- Duplicate signals from an adapter and the hook are harmless because starts are idempotent per active target.

### Negative

- The implementation depends on a documented Next.js capability whose router-transition support is still marked experimental.
- Programmatic navigation and Server Action redirects still require the hook; adapters cannot fully replace it.
- Completion requires coordination between URL commit and the root Suspense fallback rather than one framework event.

### Risks

- A Next.js upgrade may change or remove the hook. The compatibility test must fail the upgrade before release, and the upgrade owner must either adapt the bridge or replace it.
- Effect ordering could report readiness before `loading.tsx` mounts. The loading signal must use a layout effect, while URL observation uses a normal effect, and the race must be covered in integration tests.
- The hook and an adapter can report the same target in one turn. Target normalization and idempotent coalescing prevent a false superseding generation.

## Implementation Notes

- Use only the documented two-argument hook; do not enable the experimental event-metadata flag.
- Keep pure URL classification and transition reduction in `src/core/pwa/transition.ts` and browser subscription/timers in `src/core/pwa/transition-store.ts`.
- Keep the React client island in `app/navigation-transition.tsx`; wrap `useSearchParams()` in `Suspense`.
- Preserve modifier-click, download, external origin, target, and hash-only behavior in `TransitionLink`.
- Keep POST Server Action forms as ordinary forms. Their redirects enter through the router hook so the overlay does not claim that a mutation itself is a screen transition.
