# ADR-003: Evidence-Bound, Versioned Job Analysis

## Status

Accepted

## Date

2026-09-16

## Context

Job descriptions are incomplete and sometimes contradictory. An LLM can help
extract a consistent structure, but an invented salary, location, or work-mode
signal would be more harmful than an unknown value. The project already
requires provider abstraction, no invented evidence, and no ingestion writes to
applications.

## Decision

Run job analysis asynchronously through `LlmPort` using a versioned prompt and
structured schema. Store an immutable attempt with model, prompt/schema version,
input job revision, field values, provenance (`explicit`, `normalized`, or
`unknown`), confidence, bounded evidence excerpts, and outcome metadata. Missing
or conflicting fields are unknown/conflicted. Analysis can be requested by a
user who may read the job; operational prompt/version and cost details are
admin-only. No analysis result mutates applications, profile, fit score, or
source settings.

## Alternatives Considered

### Alternative 1: Free-form LLM summary

- **Description**: Store one generated paragraph and show it to the user.
- **Pros**: Quick to build and easy to display.
- **Cons**: Not auditable, difficult to compare, and encourages unsupported
  claims.
- **Why rejected**: It cannot meet the evidence and unknown-field rules.

### Alternative 2: Deterministic parser only

- **Description**: Extract fields solely with regular expressions and rules.
- **Pros**: Predictable cost and no provider dependency.
- **Cons**: Misses varied language and ambiguous structure; duplicates the
  scoring parser's scope.
- **Why rejected**: Keep deterministic normalization as a safety layer, while
  allowing an optional LLM for qualitative structure.

## Consequences

### Positive

- Users can inspect why a field was produced and rerun after source changes.
- Provider/model changes remain auditable and reversible.
- The existing application and scoring invariants stay intact.

### Negative

- Versioned schemas, evidence bounds, and retries add storage and UI work.
- Provider quotas and latency are visible product concerns.

### Risks

- Evidence excerpts can accidentally include PII; redact and bound them before
  storage and display.
- A provider can return malformed structure; validate against the schema and
  mark the attempt failed/partial rather than coercing unsafe data.

## Implementation Notes

Use the existing `LlmPort` and queue. Persist the normalized description
revision/hash used for each attempt. Keep prompt templates in reviewed code or
versioned configuration for the first release; an admin prompt editor is a
separate decision.
