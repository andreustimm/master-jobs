# ADR-002: Separate Source Definitions From Search Scopes

## Status

Accepted

## Date

2026-09-16

## Context

The same platform may expose a complete feed, a keyword endpoint, or a
paginated/partial result. The existing ingestion code can reconcile missing
fingerprints when a run is a complete source snapshot. Treating every admin
keyword search as a complete snapshot would close valid jobs that simply were
not returned by that query.

## Decision

Model a platform/source definition separately from a search scope or capture
profile. A source definition owns adapter kind, handle, enablement, capabilities,
and health. A capture profile records the query/filter and whether the adapter
guarantees complete reconciliation. Only a complete snapshot can close missing
jobs; a partial or keyword profile can upsert and score returned jobs but never
closes unrelated rows. Run records persist the resolved source/profile snapshot
so later edits cannot change what a historical run meant.

## Alternatives Considered

### Alternative 1: One source row with a mutable keyword field

- **Description**: Put search terms directly on the source and use the same
  reconciliation path for every capture.
- **Pros**: Fewer tables and a smaller form.
- **Cons**: Scope is ambiguous; partial responses can close jobs by accident.
- **Why rejected**: It conflicts with the job-retention invariant.

### Alternative 2: Treat every run as complete

- **Description**: Use the current adapter output as the platform truth no
  matter how it was queried.
- **Pros**: Straightforward closure logic.
- **Cons**: A keyword or capped page is not a complete corpus and would erase
  valid jobs.
- **Why rejected**: Data loss is unacceptable and difficult to recover.

## Consequences

### Positive

- Admin controls are expressive without coupling search to lifecycle closure.
- Run history explains exactly which scope was captured.
- New adapters can declare their capabilities honestly.

### Negative

- The data model and UI have one extra concept: a capture/search profile.
- Adapters must state whether a response is complete.

### Risks

- An adapter may incorrectly claim completeness; require a capability contract,
  tests, and conservative defaults.

## Implementation Notes

Keep local YAML as a bootstrap/import source during migration, but make the
resolved database catalog and profile snapshot explicit at the run boundary.
