# ADR-001: Hybrid Search With a Lexical Fallback

## Status

Accepted

## Date

2026-09-16

## Context

The board currently searches title and company with SQL `LIKE`. The requested
behavior must find terms in descriptions, tolerate close wording, and optionally
find semantically related roles. The project also needs to remain useful in
SQLite/local development and when no embedding provider or vector extension is
configured. Exact work-mode, location, eligibility, and lifecycle filters must
never be weakened by a relevance signal.

## Decision

Use a layered hybrid search pipeline. Apply exact filters first, then rank the
remaining rows with PostgreSQL full-text search over normalized job fields and a
trigram/proximity signal. If a current embedding exists, add semantic similarity
as another ranking signal. The lexical path is complete and authoritative for
availability; vectors are optional ordering metadata. Persist the embedding
model/version and treat absent or stale vectors as neutral fallback cases.

## Alternatives Considered

### Alternative 1: Embeddings-only search

- **Description**: Use vector similarity as the primary query mechanism.
- **Pros**: Strong discovery across different wording.
- **Cons**: Requires a provider, vector storage, reindexing, and careful hard
  filter composition; can rank an ineligible job highly.
- **Why rejected**: It violates the project's deterministic eligibility rules
  and makes local/no-provider operation fragile.

### Alternative 2: Exact substring search only

- **Description**: Extend the existing title/company `LIKE` query to include
  description text.
- **Pros**: Simple and works everywhere.
- **Cons**: Misses morphology, close spellings, and related descriptions;
  large description scans become expensive.
- **Why rejected**: It does not satisfy proximity or semantic discovery.

## Consequences

### Positive

- Search remains useful before vector infrastructure is ready.
- Exact filters retain their safety meaning.
- PostgreSQL indexes can accelerate the common path, while SQLite can use a
  documented lexical fallback during local development.

### Negative

- Ranking has more than one signal and needs explicit explanations and tests.
- Embedding backfill and model changes become operational work.

### Risks

- A poorly calibrated proximity threshold can produce noise; protect exact
  matches with deterministic weighting and telemetry.
- Different database capabilities can drift; the repository's adapter contract
  and fallback tests must keep behavior honest.

## Implementation Notes

Use `websearch_to_tsquery`/`tsvector` for user text on PostgreSQL and `pg_trgm`
for proximity where available. Keep a pure query-normalization and ranking
function for unit tests. Do not call an LLM in the interactive search request.

## Amendment (2026-09-18)

Which jobs a term returns is decided by the whole-word filter of
`term-search-target-tracks` (scorer's term boundary, `C#` and `C++` kept
literal). Full-text parsing, trigram proximity and vectors here only order
results or populate a separately labeled group; they never add to or remove
from the filtered set. See `_prd.md`, amendment A4.

## Amendment (2026-10-05) — PROPOSED, pending the owner

Issue #370, Phase 0. A4 keeps the filtered set out of reach of anything but the
whole-word filter, which is why no embedding can make a Portuguese query find a
job posted only in English. This amendment (PRD A7) proposes one bounded
exception: a curated bilingual synonym list may expand a loose query term into
an `OR` group of its listed equivalents inside the filter. It only widens the
set by listed terms, never touches a quoted phrase, keeps the term kernel's
boundary and escaping per alternative, and is off by default
(`SEARCH_SYNONYMS_ENABLED`) or by emptying the list. Vectors keep A4: they only
reorder. Not in force until the owner accepts it; the code ships behind the
flag, off.
