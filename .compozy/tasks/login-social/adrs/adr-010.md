# ADR-010: Fake OIDC issuer for end-to-end tests, accepted only outside production

## Status

Accepted

## Date

2026-10-06

## Context

E2E must exercise the real redirect, code exchange, ID-token validation and callback without contacting Google or LinkedIn. The repository has no HTTP fake/mocking server; E2E runs through `tests/e2e/run-isolated.mjs` with its own database, build and port.

## Decision

- A minimal OIDC issuer (`tests/e2e/fake-oidc.mjs`) runs inside `run-isolated`: discovery, `/authorize` (auto-consents a configured test account or simulates cancel/error), `/token`, `/jwks` with a generated RS256 key, configurable `email_verified`.
- Adapters read `JHO_OIDC_ISSUER_GOOGLE` / `JHO_OIDC_ISSUER_LINKEDIN` overrides only when `JHO_ENV` is declared `local` or `e2e` (allowlist, G27) and no Vercel variable is present; absent, misspelled or unknown values ignore the override, and a test proves it.
- The fake issuer listens on loopback only.

## Alternatives Considered

### Alternative 1: Test-only provider adapter

- **Description**: A provider that skips OIDC in E2E.
- **Pros**: Simple.
- **Cons**: Never exercises token validation.
- **Why rejected**: Owner chose the real flow.

### Alternative 2: Unit/integration only

- **Description**: No E2E of the OIDC flow.
- **Pros**: No fake server.
- **Cons**: Callback, cookies and redirects untested end to end.
- **Why rejected**: Gaps in the riskiest part.

## Consequences

### Positive

- The whole flow, including failures (cancel, error, unverified email), is testable per role (G16).

### Negative

- A small test server to maintain.

### Risks

- Override leaking to production: guarded by environment check and test.

## Implementation Notes

The E2E spec map (`config/e2e-spec-map.json`) gets a `social-sign-in` and a `sign-up` area.
