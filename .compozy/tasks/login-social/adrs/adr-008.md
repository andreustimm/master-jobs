# ADR-008: OpenID Connect through oauth4webapi behind a provider port

## Status

Accepted

## Date

2026-10-06

## Context

Social sign-in needs authorization-code flow with PKCE, `state` and `nonce`, plus full ID-token validation (signature via JWKS, `iss`, `aud`, `exp`, `nonce`) for Google and LinkedIn. The codebase has no OAuth/JWT library; the Gmail ingestion OAuth (`src/core/mail/gmail.ts`) is hand-written `fetch` with PKCE and does not validate ID tokens. The product keeps its own session (`auth_session`, cookie `jho_session`), so a framework that owns users and sessions does not fit. The existing `IdentityProvider` port (`begin(email)`/`complete(token)`) was shaped for magic links.

## Decision

- Add the dependency `oauth4webapi` (latest) and implement OIDC with it: discovery, authorization URL with PKCE S256 + `state` + `nonce`, code exchange, and ID-token validation.
- New port `OidcProvider` in `src/contexts/auth/ports.ts` with two adapters in `src/contexts/auth/infra/oidc/` (`google.ts`, `linkedin.ts`) that differ only in issuer, scopes and claim mapping. A pure `parseOidcConfig(env)` in `src/contexts/auth/domain/` returns `unconfigured | invalid | configured` per provider, naming variables, never values.
- The flow result is a `VerifiedIdentity` `{ provider, subject, email, emailVerified }`; nothing else from the provider leaves the adapter (ADR-003).
- LinkedIn uses the same developer app as publishing but requests only `openid profile email` for sign-in (never `w_member_social`).
- The transient flow state (`state`, `nonce`, PKCE verifier, intent, return path) travels in an encrypted, httpOnly, 10-minute cookie bound to the browser; it is consumed once at the callback.

## Alternatives Considered

### Alternative 1: arctic

- **Description**: Provider-specific clients with PKCE.
- **Pros**: Ready-made Google/LinkedIn clients.
- **Cons**: Does not verify the ID-token signature.
- **Why rejected**: Owner chose full validation.

### Alternative 2: Hand-written fetch + jose

- **Description**: Mirror the Gmail OAuth code and validate tokens with `jose`.
- **Pros**: No OIDC library.
- **Cons**: Re-implements spec details (discovery, nonce, PKCE) by hand.
- **Why rejected**: More code to get right.

### Alternative 3: Better Auth / Supabase Auth

- **Description**: Full auth frameworks.
- **Pros**: Linking, sessions, providers built in.
- **Cons**: Replace the product's session and user model.
- **Why rejected**: Too invasive.

## Consequences

### Positive

- Standards-compliant validation in one small dependency.
- Adding a provider is a config entry plus a claim mapper.

### Negative

- New runtime dependency to keep current (Renovate, #468).

### Risks

- Provider discovery or JWKS outage: the callback fails closed with the "could not reach provider" message (US-001.EC-3).

## Implementation Notes

The adapter files that call `fetch` must be added to `tests/outbound-transport-boundary.test.ts` (`ALLOWED`). Issuer override is only accepted outside production (ADR-010).
