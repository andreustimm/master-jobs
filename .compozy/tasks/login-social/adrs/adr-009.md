# ADR-009: Data model — identities, pending sign-ups and terms acceptance in Postgres

## Status

Accepted

## Date

2026-10-06

## Context

The runtime database is Postgres only (schema `production`, migrations in `drizzle/postgres/`). Linked identities, pending sign-ups (manual awaiting code, social awaiting the form) and terms acceptance must persist across serverless instances. The per-IP sign-up cap (3/hour) cannot use the in-memory limiter in `src/core/rate-limit.ts`, which is per instance. Additive migrations ship automatically; non-additive ones need manual review (ADR 0028).

## Decision

All changes are additive:

- `auth_identity`: `id`, `user_id` → `auth_user` **ON DELETE CASCADE**, `provider` (`google`|`linkedin`), `subject`, `email_at_link`, `origin` (`automatic`|`manual`), `linked_at`, `last_used_at`. Unique `(provider, subject)` and `(user_id, provider)`.
- `auth_signup`: one row per pending sign-up. `id`, `kind` (`manual`|`social`), `token_hash` (unique; random token in cookie for social, sent code flow for manual), `email`, `locale`, `role` (null until chosen for social), `name`, `headline`, `cv_text`, `password_hash` (manual), `provider`/`subject` (social), `code_hash`, `code_attempts`, `code_sent_at`, `codes_sent_hour` window data, `ip_hmac`, `terms_version`, `privacy_version`, `created_at`, `expires_at`, `completed_at`, `user_id` → `auth_user` **ON DELETE SET NULL** (set on completion).
- `auth_user` gains nullable `email_verified_at`, `terms_version`, `privacy_version`, `terms_accepted_at`, `signup_origin` (`admin`|`manual`|`google`|`linkedin`), `locale`.
- Per-IP cap counts `auth_signup` rows with `completed_at` in the last hour for the same `ip_hmac`, inside the completion transaction with `SELECT … FOR UPDATE` on a per-IP advisory lock (G13: reserve before await).
- `ip_hmac` = HMAC-SHA256(IP, `JHO_SIGNUP_IP_SECRET`); raw IPs are never stored. Rows older than 24 h (pending) or 30 days (completed) are purged by the existing maintenance job.
- New tables are registered in `scripts/migration/select-production.ts` (`postSnapshotTables`) so `tests/postgres-schema.test.ts` passes.

## Alternatives Considered

### Alternative 1: Signed cookies only for pending sign-ups

- **Description**: Keep pending data in encrypted cookies.
- **Pros**: No table.
- **Cons**: CV text exceeds cookie size; no server-side cap or replay protection.
- **Why rejected**: Doesn't fit the CV or the per-IP cap.

### Alternative 2: Reuse `auth_login_token`

- **Description**: Store codes as another `purpose`.
- **Pros**: Fewer tables.
- **Cons**: Pending sign-ups have no user and carry profile data.
- **Why rejected**: Wrong shape.

## Consequences

### Positive

- Additive migration; automatic deploy path.
- One place to count, expire and audit sign-ups.

### Negative

- CV text of unconfirmed sign-ups lives up to 24 h in the database.

### Risks

- Missing `JHO_SIGNUP_IP_SECRET` in production: the configuration check refuses sign-up (fail closed) and the admin status shows it.

## Implementation Notes

Generate with `pnpm db:generate`; add an upgrade test (`tests/postgres-upgrade-*.test.ts` pattern). Every FK declares `onDelete` (G20).
