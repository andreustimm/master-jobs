# ADR-003: LinkedIn and Google only for authentication, keeping provider subject and verified email only

## Status

Accepted

## Date

2026-10-05

## Context

Inviolable rule 1 (`AGENTS.md`, G01, `docs/linkedin-policy.md`) forbids acquiring LinkedIn data and permits only official APIs. The current policy fixes the LinkedIn OAuth scope to exactly `openid profile w_member_social`, for publishing. Signing in needs `openid profile email` and must not request `w_member_social`. LinkedIn's API terms require consent to store profile data, deletion on request, and forbid combining it with other LinkedIn content. The product's bottleneck is decision, not discovery; profile name, photo or headline do not help decide on a job.

## Decision

- LinkedIn sign-in uses only the official "Sign In with LinkedIn using OpenID Connect" product; Google sign-in uses Google's OpenID Connect. Scopes are the minimum for identity (`openid`, `email`, and `profile` only where the provider requires it to return the email).
- The product stores, per linked identity, only the provider, the subject, the verified email at link time, the link date and the last-use date. No name, photo, headline, profile URL, or provider tokens are stored or logged.
- Provider data never feeds the candidate profile, the public profile `/p/<slug>`, sourcing, scoring or any job data.
- Unlinking deletes the identity record.
- Rule 1, G01 and `docs/linkedin-policy.md` are amended in the same change that ships LinkedIn sign-in, adding "OpenID Connect for authentication only, without `w_member_social`" to the permitted uses and keeping the publishing scope invariant separate.

## Alternatives Considered

### Alternative 1: Use name and photo as the account avatar

- **Description**: Store name/photo for display only.
- **Pros**: Friendlier account menu.
- **Cons**: Stores LinkedIn profile data, needs consent handling and deletion; adds nothing to decisions.
- **Why rejected**: The owner chose minimal data.

### Alternative 2: Prefill the candidate profile from LinkedIn

- **Description**: Import name/headline/photo into the candidate.
- **Pros**: Faster onboarding.
- **Cons**: Reopens rule 1 (acquiring LinkedIn data) and the API terms' combination ban.
- **Why rejected**: Conflicts with rule 1.

## Consequences

### Positive

- Rule 1 stays unambiguous: authentication only, no profile data.
- Unlinking fully erases what the product knew from the provider.

### Negative

- Accounts show no avatar or provider name.

### Risks

- Future requests to reuse provider data must go through a new ADR and a rule 1 change.

## Implementation Notes

Provider client secrets live as environment variables (rule 16/G41); only variable names may be recorded.
